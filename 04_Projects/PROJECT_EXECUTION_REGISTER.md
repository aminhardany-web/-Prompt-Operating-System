Status: OPERATIONAL

## 1. Mission

This register is the operational entry point for the user's existing real projects inside the existing Prompt OS / PKEA environment.

The objective is not to create another architecture. The objective is to take the user's existing project material—Library content, relevant chat history, documents, research, books, translations, work material and other project evidence—and turn it into usable, traceable project work.

The existing architecture is frozen. No new operating-system layer, framework, registry model or parallel project architecture is introduced by this register.

## 2. User-facing operating rule

The user works by project and desired outcome, not by system component.

Examples:

- Continue the strategic ports project.
- Continue the containerization book.
- Recover and organize ISPS research.
- Work on the port-management Library.
- Analyze procurement and contract regulations.
- Continue the Book Translation Engine.

EPKOS, Prompt OS, Prompt Bank, REP, HVS-001, RA-001 and PKEA remain behind the operational interface and perform their existing roles.

## 4. Project corpus rule

For every project, the source corpus can come from the user's available Library, conversation history, uploaded documents or other explicitly available project material.

Recovery must preserve:

- original source text;
- provenance/source location;
- project association;
- date when available;
- version when available;
- existing prompt text without rewriting when the item is a prompt;
- relationship between source, decision, claim and output when evidence exists.

No missing source material may be invented.

## 5. Operational flow

Existing material
→ project identification
→ source preservation
→ supported ingestion into PKEA
→ document registry / identity
→ claims and evidence
→ conflicts / dependencies / gaps
→ existing Prompt OS / Prompt Bank workflows
→ project work
→ human review
→ usable output with traceability

This is an execution flow, not a new architecture.

## 6. File coverage

The current PKEA baseline supports MD/Markdown, TXT, JSON, CSV and DOCX input.

A project must not be marked as fully ingested when its material exists only in an unsupported or unprocessed format.

PDF, scanned images, complex spreadsheets, presentations and other formats require an actual verified ingestion path before their content can be claimed as processed. No silent assumption of coverage is permitted.

## 7. Operational status definitions

REGISTERED = project is recorded, but its complete source corpus has not yet been evidenced in the repository/runtime.

INGESTED = the available supported corpus has been imported and source identity/provenance is preserved.

PROCESSED = PKEA has processed the ingested corpus and produced its evidence-oriented outputs.

ACTIVE = the project is being used for real work through the existing system.

OPERATIONAL = the project has an available corpus, provenance is preserved, supported processing has been verified, and at least one useful project output is traceable to source material.

No project is declared OPERATIONAL merely because a folder, README, prompt category or project name exists.

## 8. Current status policy

The projects above are registered for execution. Their actual corpus availability is not inferred from their titles.

The GitHub repository is the operational home of the existing system, but it is not evidence that the user's entire ChatGPT Library or historical chat corpus has already been transferred into GitHub.

Therefore this register intentionally distinguishes project registration from corpus ingestion.

## 9. Final execution principle

Stop expanding architecture.

Use the existing system on the user's real work.

The success criterion is not the number of prompts, protocols, folders or documents created. The success criterion is whether the user's real projects become easier to continue, search, verify, reuse and turn into reliable outputs.
