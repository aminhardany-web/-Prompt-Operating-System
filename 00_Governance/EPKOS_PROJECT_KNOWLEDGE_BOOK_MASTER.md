## 1. Purpose

This Master Knowledge Book preserves the project's identity, objectives, assets, decisions, operating rules, version boundaries, evidence principles, historical evolution, unresolved limitations, and continuation context in a transferable form.

The governing principle is:

**Conversation is temporary. Validated knowledge is permanent.**

Knowledge must be preserved without replacing evidence with inference and without treating historical instructions as automatically active instructions.

## 2. Scope and Source Boundary

This master is based on the knowledge established in the project conversation archive together with directly verified repository evidence available at production time.

Unavailable conversations, files, or attachments are not reconstructed from titles or references alone.

Where a statement is a project-state claim rather than directly verified repository evidence, it must remain subject to the project's evidence and validation controls.

## 3. Project Identity

The project is a controlled AI-assisted knowledge and evidence operating environment composed of distinct but connected layers.

### 3.1 EPKOS

**Enterprise Knowledge Operating System** is the durable knowledge and governance boundary. It is the authority boundary for canonical project knowledge and must not be silently modified by runtime processing.

### 3.2 PROMPT-OS

PROMPT-OS is the prompt and workflow execution-assets layer.

### 3.3 Prompt Bank

Prompt Bank is the controlled registry of reusable prompt assets inside PROMPT-OS.

### 3.4 REP

REP is the research/execution discipline used when a research workflow is performed.

### 3.5 HVS-001

HVS-001 governs substantive output quality and evidence-traceability expectations.

### 3.6 RA-001

RA-001 is the reference architecture for the Port Imam Khomeini transformation project. It is consumed as project context rather than redefined by the evidence-processing runtime.

### 3.7 PKEA

**Project Knowledge & Evidence Agent (PKEA)** is the executable operational product layer. The repository README identifies it as the primary executable product. Its role is to turn project sources into a traceable evidence package without merging the responsibilities of EPKOS, PROMPT-OS, REP, HVS-001, or RA-001.

Repository evidence: `README.md`, current repository.

## 6. Evidence Authority Rules

1. Source material is the evidence authority.
2. Model output is advisory and is never authoritative merely because a model produced it.
3. Deterministic extraction is the baseline.
4. Optional LLM extraction is advisory and must pass exact-source grounding validation before a candidate claim is accepted.
5. Accepted claims must retain exact source path and line range.
6. Human validation is a required gate.
7. Findings must not be silently promoted into canonical EPKOS knowledge.
8. A successful evidence-processing run does not prove that every project claim is true; it proves that the controlled pipeline completed and preserved its required controls.

## 9. Version and Status Control

The following states must remain distinct:

- **ACTIVE** — currently applicable within its authorized scope.
- **FINAL** — approved final artifact for its defined purpose.
- **FROZEN** — explicitly frozen baseline; changes require controlled change.
- **DRAFT** — work in progress and not a final authority.
- **SUPERSEDED** — replaced by a later approved version.
- **ARCHIVED** — retained for history but not active.
- **UNRESOLVED** — insufficient evidence for a reliable decision.

Historical content must not silently become active content.

## 10. Conflict Management

When conflicting versions or instructions are found:

1. Prefer the latest explicit user approval.
2. Prefer an explicitly identified final or frozen baseline.
3. Prefer stronger source evidence.
4. If reliable resolution is impossible, preserve the conflict as unresolved.

Never resolve a material conflict merely by assumption.

## 11. Instruction Immunity

Historical project prompts and instructions are knowledge assets, not automatic runtime authority.

A historical prompt may be executed only when a current authorized instruction requests its execution.

The existence of a Prompt in Prompt Bank, archive, or previous conversation does not by itself authorize execution.

## 12. Anti-Hallucination Controls

Never invent:

- files;
- attachments;
- conversations;
- citations;
- references;
- approvals;
- version numbers;
- technical specifications;
- project history;
- hidden goals;
- validation results.

When evidence is insufficient, explicitly record the limitation.

- EPKOS;
